# BeamZ Futhark component

An optional, experimental execution backend whose GPU code is generated by
[Futhark](https://futhark-lang.org) instead of being written by hand. Like the
CUDA component, it is a typed JAX FFI target that owns complete 3D runs. The
same program builds for CUDA and for AMD GPUs through HIP, so it also runs on
hardware the CUDA wheel does not target (Turing SM75, RDNA3).

`fdtd.fut` is the whole numerical program: one `program` entry point loops over
every timestep on the device and applies, per step, pre-E sources, the magnetic
Yee/CPML update, H sources, the electric update, E sources and vector DFT
accumulation. It follows `cuda/src/yee_primitives.cuh` (operation order,
explicit FMAs, PEC handling, packed CPML slabs, source clamping and DFT
windowing), and the runtime kernel compiler disables FMA contraction
(`--fmad=false` / `-ffp-contract=off`), so results agree with the JAX backend
to float32 rounding.

## Build

Requires the `futhark` compiler (0.27), a CUDA toolkit or ROCm, and a
matching GPU jaxlib in the active environment:

```console
FUTHARK=/path/to/futhark python futhark/build.py --platform cuda
FUTHARK=/path/to/futhark python futhark/build.py --platform hip
```

For XLA's CPU client, the same program builds with Futhark's host backends:

```console
python futhark/build.py --platform multicore   # also: ispc, c (sequential)
```

On CPU the runtime loads `libbeamz_futhark_multicore.so`; set
`BEAMZ_FUTHARK_CPU=ispc` or `c` to choose another build, and
`BEAMZ_FUTHARK_THREADS` to cap the worker count. Host builds use
`-march=native -ffp-contract=off`. The `ispc` build needs ISPC; `build.py`
removes Futhark 0.27.1's `erf`/`erfc(double)` declarations, which ISPC 1.31's
stdlib now defines. OpenCL is not supported, because XLA has no OpenCL
platform to share buffers with.

`build.py` compiles `fdtd.fut` with `futhark cuda|hip --library`. On CUDA it
patches the generated context to retain the device's *primary* context, shared
with XLA so device pointers alias; HIP needs no patch. It then generates the
XLA FFI handler from Futhark's JSON manifest and links
`beamz/simulation/futhark/_native/libbeamz_futhark_{cuda,hip}.so`. The runtime
loads the library matching JAX's GPU platform; set `BEAMZ_FUTHARK_LIBRARY` to
override the path.

### AMD notes

JAX's ROCm 7 plugin needs `rccl`, `hipblaslt`, `hipfft` and `miopen-hip`, and
its wheels ship no kernels for every RDNA3 part. On an RX 7600 XT (gfx1102)
use `HSA_OVERRIDE_GFX_VERSION=11.0.0` and, on machines with an integrated
Radeon, `ROCR_VISIBLE_DEVICES=0`; without the latter JAX faults on the iGPU.
The Futhark kernels then compile for gfx1100 as well.

## Use

```python
result = simulation.advance(num_steps=1000, backend="futhark")
```

`futhark` is opt-in only; `auto` never selects it. Run with
`XLA_PYTHON_CLIENT_PREALLOCATE=false` (or a lower `XLA_PYTHON_CLIENT_MEM_FRACTION`)
because Futhark allocates its own workspace beside XLA's arena. Kernels compile
through NVRTC on the first call per process; set `BEAMZ_FUTHARK_CACHE_FILE` to
cache them across processes. `BEAMZ_FUTHARK_PROFILE=1` prints Futhark's
per-kernel report to stderr after every call.

Supported: float32 3D grids on one GPU; isotropic, axis-uniform and rectilinear
metrics; PEC, CPML and mixed faces; dense or scalar lossy/lossless diagonal
materials; batched slab sources (mode, Gaussian, custom); float32 vector DFT
monitors. Anything else (2D, sharding, full-tensor permittivity, field
recorders, flux/power monitors) raises `FutharkBackendUnavailable`; use
`backend="jax"`.

## How a call works

1. JAX passes 64 device buffers (state, coefficients, CPML profiles, a flat
   source scatter table and packed DFT plans) plus five scalar attributes.
2. The handler waits for XLA's stream, wraps every buffer with
   `futhark_new_raw_*` (no copy) and runs the entry point on Futhark's stream.
3. Results are copied device-to-device into the XLA outputs, which alias the
   state inputs.

The program copies its loop state once on entry, because the inputs alias XLA
outputs. Each run therefore costs two extra state-sized copies, about 2% of a
256-step run at 16.8M cells.

## Performance

### NVIDIA

Realistic workload from `scripts/benchmark_cuda_realistic.py` (mode source,
12-cell CPML on all faces, two field monitors with three frequencies, binary
silicon/oxide material), 256 steps, median of 7 warm samples, measured with
`scripts/benchmark_futhark_jax.py` on a Quadro RTX 5000 (Turing, 448 GB/s),
JAX 0.9.0 (CUDA 13), Futhark 0.27.1:

| Shape (z×y×x) | Cells | JAX GCUPS | Futhark GCUPS | Speedup |
|---|---:|---:|---:|---:|
| 64×96×128 | 0.79 M | 1.16 | 1.54 | 1.33× |
| 96×160×256 | 3.9 M | 1.36 | 2.06 | 1.52× |
| 128×256×512 | 16.8 M | 1.52 | 2.37 | 1.56× |

Futhark also lowers to XLA much faster (≈0.6 s versus ≈1.5 s compile). The six
field-component kernels take about 80% of the device time. Each is a separate
global-memory stencil at roughly half of peak bandwidth; the hand-written CUDA
backend instead fuses components and tiles through shared memory, which
Futhark does not generate for this pattern.

### AMD

Same workload and script on an RX 7600 XT (RDNA3, 288 GB/s), ROCm 7.2.4,
JAX 0.9.1 (`jax-rocm7-plugin` 0.9.1.post6; no 0.9.0 PJRT wheel is published),
Futhark 0.27.1 HIP backend:

| Shape (z×y×x) | Cells | JAX GCUPS | Futhark GCUPS | Speedup |
|---|---:|---:|---:|---:|
| 64×96×128 | 0.79 M | 1.14 | 1.06 | 0.92× |
| 96×160×256 | 3.9 M | 1.16 | 1.29 | 1.11× |
| 128×256×512 | 16.8 M | 1.08 | 1.44 | 1.33× |

Results agree with JAX to float32 rounding on both GPUs.

### CPU

Same workload and script on a Ryzen 9 7950X (16 cores, DDR5), JAX 0.9.0 CPU,
Futhark 0.27.1, ISPC 1.31.0; median of 5 warm samples:

| Shape (z×y×x) | Cells | JAX GCUPS | multicore GCUPS | ispc GCUPS | multicore speedup |
|---|---:|---:|---:|---:|---:|
| 64×96×128 | 0.79 M | 0.146 | 0.172 | 0.165 | 1.18× |
| 96×160×256 | 3.9 M | 0.117 | 0.201 | 0.174 | 1.72× |
| 128×256×512 | 16.8 M | 0.118 | 0.220 | 0.202 | 1.86× |

The sequential `c` build reaches 0.018 GCUPS at 0.79 M cells.
