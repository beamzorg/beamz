# Test the local CUDA branch in RunPod JupyterLab

Use a **Pod with one full H100 SXM 80 GB**, a CUDA **12.8 development** image,
Python **3.11 or 3.12**, and JupyterLab already enabled. The ordinary 80-GB H100
PCIe is also usable but has a different bandwidth target; record the exact SKU.
Start with at least 64 GB host RAM, a 40-GB container disk and a 100-GB persistent
volume mounted at `/workspace`. Prefer 128 GB host RAM for substantially larger
domains. Run one GPU benchmark process at a time.

Official RunPod PyTorch templates include JupyterLab. Choose the CUDA 12.8
**devel** variant so `nvcc` is present; PyTorch itself is not used by BeamZ.
Set a private Jupyter password, expose HTTP port 8888, deploy, then select
**Connect → Jupyter Lab / HTTP 8888**. See [RunPod connection instructions](https://docs.runpod.io/pods/connect-to-a-pod).
Use a [network volume](https://docs.runpod.io/pods/storage/types) if files must
survive deletion of the Pod. Keep source, environment and results in `/workspace`.

## Transfer the actual working branch

The optimization work is still local and unpushed. Cloning GitHub alone will not
reproduce it. From the local worktree, create a source snapshot:

```bash
python scripts/package_runpod_source.py --output .cache/runpod/beamz-h100-source.tar.gz
```

Upload that archive through JupyterLab's file browser into `/workspace`. It
includes uncommitted source changes and an independent Git snapshot for benchmark
metadata. `RUNPOD_SOURCE.json` records the original branch commit and file hashes.
It excludes local shared libraries, environments, caches, repository history,
the untracked waveguide notebook and the large benchmark archives. It does not
push or modify the original branch's Git history.

In a JupyterLab **Terminal**:

```bash
cd /workspace
# Extract into a fresh location, not over an existing checkout.
test ! -e beamz-h100 && tar -xzf beamz-h100-source.tar.gz
cd beamz-h100
bash docker/runpod/setup-h100.sh
```

The setup installs the locked development, test and GDS dependencies, builds
BeamZ's Rust raster extension, installs **JAX 0.9.0 with pip-managed CUDA 12
libraries**, and builds the CUDA extension for **SM90**, Release, fast math OFF.
It uses `/workspace/.venvs/beamz-h100` and registers **BeamZ H100 (CUDA)** with
Jupyter. Build concurrency defaults to two processes; `BEAMZ_BUILD_JOBS` changes
that. Native compilation can take several minutes.

The Pod must provide the NVIDIA host driver and CUDA toolkit; do not install a
host GPU driver inside the container. JAX documents CUDA 12 driver requirements
and why inherited `LD_LIBRARY_PATH` can select incorrect libraries in its
[installation guide](https://docs.jax.dev/en/latest/installation.html).
The registered kernel clears that variable to use pip-managed CUDA libraries.
This setup downloads dependencies and the Rust toolchain; it is not an offline
installer. It does not change GPU power limits.

Refresh JupyterLab, open a notebook and select **BeamZ H100 (CUDA)**. Run:

```python
import os
import sys
from pathlib import Path
import jax
from beamz.simulation.backend import cuda_backend_status

ROOT = Path('/workspace/beamz-h100')
os.chdir(ROOT)
print(sys.executable)
print(jax.devices())
print(cuda_backend_status().as_dict())
assert jax.default_backend() == 'gpu'
assert cuda_backend_status().available
```

## Verify correctness, then measure

In a notebook cell, run small seeded FP32 layout tests in a separate process:

```python
import subprocess
subprocess.run([
    sys.executable, '-m', 'pytest', '-q',
    'tests/hardware/test_cuda_storage.py',
    '-k', 'test_cyclic_graph and fp32 and ordinary',
], cwd=ROOT, check=True)
```

These verify full state against the branch canonical layout, including sources,
CPML and monitors. They do not establish equality with origin/main; known CPML
tolerance discrepancies remain in the RTX3090 comparisons.

Use the following notebook cell for the exact four realistic RTX3090 workloads.
Each case runs in a fresh subprocess so memory and graph caches are released:

```python
import json
import os
import subprocess

cases = [
    ('short_x', (1126, 297, 65), 'binary'),
    ('long_y', (104, 1083, 180), 'smooth'),
    ('flat_z', (110, 202, 866), 'binary'),
    ('irregular', (325, 203, 312), 'smooth'),
]
results = ROOT / 'results/h100-default'
results.mkdir(parents=True, exist_ok=False)
env = {k: v for k, v in os.environ.items() if not k.startswith('BEAMZ_CUDA_')}
env.update(PYTHONPATH=str(ROOT), XLA_PYTHON_CLIENT_PREALLOCATE='false',
           XLA_PYTHON_CLIENT_MEM_FRACTION='.80')
for name, shape, material in cases:
    output = results / f'{name}.json'
    command = [
        sys.executable, 'scripts/benchmark_cuda_realistic.py',
        '--shape', *map(str, shape), '--steps', '256', '--pml', '12',
        '--material', material, '--source', 'mode', '--monitor-type', 'mode',
        '--monitors', '2', '--frequencies', '3', '--warmups', '4', '--samples', '9',
        '--state-digests', '--output', str(output),
    ]
    with (results / f'{name}.log').open('w') as log:
        subprocess.run(command, cwd=ROOT, env=env, stdout=log,
                       stderr=subprocess.STDOUT, check=True)
    record = json.loads(output.read_text())
    print(name, record['median_gcups'], 'GCUPS', record['storage_axes'])
```

A failed process leaves its diagnostic output in the corresponding `.log`.
JSON contains timings, source/native fingerprints, GPU details, state hashes,
field precision and CPML precision. These are warm executable rates, including
storage conversion but excluding setup/JIT and mode solving. Save
`nvidia-smi -q` and `.cache/runpod/installed-packages.txt` with the results.

**This is the H100 default baseline.** The automatic geometry selector currently
targets RTX3090 and automatic core fusion targets SM86. Do not label default
H100 results as measurements of the selected RTX3090 schedules. Next, repeat in
fresh result directories with explicit `BEAMZ_CUDA_STORAGE_AXES=012`, `120`, and
`201` in the subprocess `env`. Compare `state_sha256` against the canonical run
for the same shape/material before accepting timing differences. The physical
grid, CPML12 and FP32 remain identical. Test forced fusion separately only after
H100 parity checks; `cuda_hopper` is a separate experiment, not the backend that
produced the RTX3090 results.

Repeat promising cases in reverse order before drawing performance conclusions.
For larger domains, increase **all three dimensions together**, keep CPML12 and
the monitor/source workload fixed, and check host/GPU memory before each increase.
Doubling every axis means **eight times the cells**, not twice the memory.
Start with a smaller size increase rather than launching every doubled case at
once. Longer requests, e.g. 1024 steps, additionally test chunking and sustained
execution; use a new results directory and the corresponding source duration.

For an origin/main comparison, use a separate checkout and build its matching
CUDA extension; do not reuse this branch's `.so` with main's Python ABI. This
bundle is sufficient to compare H100 against the recorded RTX3090 workloads;
the supplied random-comparison runner is RTX3090-specific and is not an H100
main-versus-branch driver.

## Validation status of this setup

The setup script is intended to run on the remote Pod. Local checks cover shell
syntax, lockfile export, SM90 CMake generation, and source-bundle integrity.
An end-to-end installation on RunPod and H100 execution have not been performed.
The existing `Dockerfile` is an alternative base environment; by itself it does
not install the unpushed branch or compile this CUDA component. No Pod, image
registry publication or remote upload is performed by these local tools.
