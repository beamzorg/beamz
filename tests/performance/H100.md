# H100 CUDA performance protocol

## Existing observations

Before the schema-v2 harness existed, realistic BeamZ workloads reached roughly
16–17 GCUPS on one H100 and more than 40 GCUPS on four H100s that were not fully
saturated. These are useful engineering anchors supplied by the project, but not
normalized baseline records: the exact shape, feature set, H100 variant, clocks,
JAX version, and timing boundary were not captured here. They must not be used as
automated regression gates.

The first hardware run of `scripts/benchmark_h100.py` becomes the normalized JAX
baseline. Keep its raw JSON with the machine configuration and NVIDIA SMI topology.

## Canonical profiles

| Profile | Purpose | Timed features |
| --- | --- | --- |
| `bare_3d` | Upper-bound stencil throughput | 3D float32 Yee update, homogeneous material, PEC faces |
| `realistic_3d` | User-representative throughput | heterogeneous dielectric, six-face CPML, Gaussian source, four-component plane DFT monitor |

Both profiles default to `128 × 256 × 384` cells in `(z, y, x)` storage order and
500 full timesteps. GCUPS means aggregate material-cell updates per second; it is
not multiplied by six field components. Multi-GPU results report aggregate GCUPS
and the exact device count.

## Controlled run

1. Record GPU model and memory, driver, CUDA, clocks/power limit, CPU, NUMA binding,
   JAX/JAXLIB, Python, BeamZ commit, and visible device topology.
2. Use persistence mode and fixed application clocks when the machine permits it.
3. Run each profile and backend in a fresh process. Do not compare a MIG slice with
   a full H100 or mix SXM and PCIe baselines.
4. Retain at least five warm compiled-executable samples and five public-path
   samples. The harness performs an additional unreported allocator warmup.
5. Report median GCUPS plus all raw timings and peak memory. Never report the best
   sample alone.

The target is 15–35 realistic GCUPS on one H100, followed by near-linear scaling
through 2, 4, and 8 GPUs. These are engineering targets, not achieved guarantees.
Only `jax` and `cuda_streamed` execution paths are supported. Historical results
and measured bottlenecks are in `benchmarks/reports/H100_BACKEND_COMPARISON.md`;
the implementation analysis and proposed acceptance gates are in
`benchmarks/reports/H100_PERFORMANCE_ANALYSIS.md`.

Report strong scaling (fixed global domain) separately from weak scaling (fixed
cells per GPU). Always compare against the optimized one-GPU implementation,
not a deliberately slower distributed one-rank baseline. State the workload,
monitor frequencies, precision, physical duration, and timing boundary for each
target. Preserve full numerical and continuation checks when changing schedules.
